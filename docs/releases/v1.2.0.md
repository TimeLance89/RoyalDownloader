# RoyalDownloader v1.2.0

## Highlights

This Stable release brings the complete reviewed Overnight frontend to main:
native JavaScript modules, explicit feature dependencies, reliable mobile
carousels, substantially fewer rendered cards, and mandatory real-browser
regression gates. The existing Royal design, rails, logical titles and image
quality remain intact. There is no framework migration or application build step.

The release delta is measured from published **v1.1.0**, commit
`31d91417c4d45bb054140de60b7125ac6b7dbd78`, to Overnight
`e5c82699648b0c0d89f36709c9b25fa6abfd0fe8`, followed by main-based release
preparation. v1.1.0 incorrectly reported application version 1.0.0; v1.2.0
aligns the tag, application metadata, capabilities, installation guide and notes.

## Frontend architecture

- Replace historical runtime/screen scripts and browser-global feature functions
  with native ES modules in `core/`, `shared/`, `features/`, `shell/` and
  `composition/`. HTTP belongs to `core/api.js`; WebSocket connections and
  reconnect ownership belong to `core/websocket.js`.
- Give features explicit state ownership and mount/refresh/unmount lifecycles.
  Lifecycle scopes release listeners, timers and subscriptions when a view ends.
- Split the former large composition root into domains including Home, Discovery,
  Downloads, Search, Profile, Subscriptions, Settings and Integrations. Group
  application dependencies by domain rather than hiding them in a global container.
- Remove `sharedPresentation`, eliminate cyclic module imports, and inject
  dependencies directly. Move domain actions out of the shell; keep shell duties
  focused on navigation and shared application chrome.
- Reuse shared cards, rails, dialogs, feedback and loading primitives; consolidate
  design tokens while preserving computed styles. Automated tests enforce module
  resolution, import direction, no cycles, no old runtime scripts, and transport
  ownership. See [the architecture guide](../FRONTEND_ARCHITECTURE.md).

## Faster UI on lower-end hardware

The full triple-copy carousel strategy is replaced by bounded, viewport-aware
edge buffers. All logical titles remain available; no rail or title is removed.
Offscreen rail sections use measured intrinsic sizing and visibility/resize
observers to skip distant rendering without collapsing page height. Artwork
geometry reads and writes are batched; already-started images avoid repeat work.
Lazy loading and asynchronous decoding remain, with unchanged image quality.

In the deterministic seven-rail fixture (97 logical entries), complete card DOM
structures fall from **257 to 137 on desktop (46.7% fewer)** and **257 to 117 on
mobile (54.5% fewer)**. Total DOM nodes fall from **6,320 to 4,640** and **6,320 to
4,360**, respectively.

Representative paired Chromium CI medians from the documented three-sample
profiles, using the same runner and frozen pre-performance baseline:

| Profile | Initial render, ms | Total blocking time, ms | Layout duration, ms |
|---|---:|---:|---:|
| Desktop, 4x CPU slowdown | 208.3 → 137.4 | 529 → 386 | 99.7 → 69.2 |
| Desktop, 6x CPU slowdown | 305.1 → 218.0 | 1092 → 860 | 147.2 → 105.7 |
| Mobile, 4x CPU slowdown | 196.2 → 122.2 | 497 → 308 | 79.5 → 56.1 |

These are reproducible fixture results, not guarantees for every device or NAS.
The baseline is `d3aada9`; this representative paired run is `36302825485`.
Later final-code measurements and raw results are retained in
[the performance report](../FRONTEND_PERFORMANCE_RESULT.md). Long-task counts and
LCP do not improve in every sample; reduced blocking duration is the more stable
finding. The harness uses deterministic artwork and mock APIs, not field INP or
real provider/network throughput. Fonts, blur, shadows and typography were audited
and retained; there is no automatic low-quality mode.

## Mobile browser experience

- Restore horizontal touch interaction, including the hidden navigation scrim
  that previously intercepted input. Touch and pen use native browser panning.
- Stop changing `scrollLeft` on initial touch or on every scroll event. Loop
  correction waits for gesture/momentum settling, using `scrollend` with a quiet
  debounce fallback where unavailable.
- Distinguish a tap from a swipe: taps still open details; dragging does not
  accidentally open a card. Vertical page scrolling can begin over a card.
- Preserve logical anchors through loop boundaries, repeated swipes, tab/history
  navigation, background refresh and portrait/landscape changes. Fix a detail
  poster variable-shadowing error exposed by real card taps.
- Cover smartphone and tablet sizes 390×844, 430×932 and 768×1024 with touch
  pointers and device scaling. Chromium exercises continuous native gestures;
  WebKit covers real taps and scroll/resize contracts.

## Personalization and multi-user

Household accounts, isolated sessions, first-login password setup, taste
onboarding, recommendations and the Profile Hub **already existed in v1.1.0**.
This release preserves them within explicit profile/home/discovery modules;
they are not claimed as newly introduced features.

The durable `PersonalRequestStore` also already existed. Its separation remains:
**Personal Request ≠ Download Job ≠ Queue**. Personal history survives queue
cleanup and server restart, stays isolated per user, and deduplicates retries by
job identity. The migrated profile and Home views retain recent personal requests.

## Reliability and persistence

- Expose a normalized integration-health contract: `healthy`, `degraded`,
  `offline`, `auth_failed`, `disabled`, `unknown`. Frontend status uses explicit
  controller facts, not translated error text or Jellyfin media ownership.
- Broadcast committed movie-subscription save/removal and watchlist-removal
  snapshots so other views update promptly. Failed persistence emits no false
  successful snapshot.
- Keep the compatibility `web/i18n.js` file required by already-installed updater
  archive validators, while actual localization runs through native modules.
- Preserve authentication, queue ownership, provider configuration, storage paths,
  update channels and durable data formats. No destructive migration is added.

## Testing and release safety

The required `verify` check now depends on Chromium browser smoke, setup/login,
mobile gesture tests (including no-`scrollend` fallback), WebKit mobile validation,
frozen CSS equivalence, populated-carousel visual comparison, performance/content
budgets and offscreen layout budgets. Architecture layers, cycle detection and
core contracts are tested alongside Python, security scans, CodeQL, container
build/validation, first-run authentication, queue persistence/restart and E2E.

The existing RC3 upgrade/rollback/backup gate remains. A separate gate uses the
actual published v1.1.0 source to seed accounts, a live session, queue, subscriptions,
user taste and request history, settings, providers, Jellyfin configuration and
media paths; it verifies candidate startup twice, rollback and restored backups.
An independent runtime volume marker is preserved throughout the sequence.

## Compatibility

This is a compatible minor release. Existing HTTP, `/api/v1`, WebSocket,
Docker-volume, deployment and update-channel contracts remain. Integration health
adds structured fields. Stable still follows `main`; Overnight follows `overnight`.
Internal JavaScript paths are reorganized and are not a supported third-party API.
Use a modern browser with native ES-module support.

## Upgrade

1. Back up `.env`, `data/`, `runtime/` and the current source revision; stop the
   stack while copying mutable files. Keep media-volume backups separately.
2. Use the normal Stable updater, or fetch tags and check out `v1.2.0`, then rebuild
   using the existing Docker Compose configuration and mounted volumes.
3. Verify `/api/health` and `/api/v1/capabilities`: `application_version` must be
   `1.2.0`; `build` identifies the active source separately.
4. Restart once. Check accounts, sessions, queue, subscriptions, personal history,
   settings, providers, Jellyfin, media paths and the selected update channel.

See [release operations](../RELEASE.md) for exact commands. Do not delete data or
runtime directories, reset settings, or recreate users as an upgrade step.

## Rollback

Use the existing runtime rollback to the previous complete source/dependency set,
or stop the stack and rebuild the recorded previous source revision with the same
volumes. If necessary restore the matching `data/` and `runtime/` backup together.
Rollback to v1.1.0 retains its historical application-version display of **1.0.0**;
verify its source SHA, not that incorrect historical label. Recheck health, account
access, queue recovery and mounted media after rollback.

## Known limitations

- Providers can change availability and protection independently of Royal.
- Playwright's public WebKit API does not inject continuous touch swipes. WebKit
  tests are not a physical iPhone/Safari momentum certification.
- Fixture benchmarks do not predict live-network LCP, field INP or all GPU costs.
- Stable tracks `main`, so select manual updates when a tag-pinned installation
  must remain on exactly v1.2.0.
