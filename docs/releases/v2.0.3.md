# RoyalDownloader v2.0.3

RoyalDownloader v2.0.3 promotes the reliability, security and settings changes
since v2.0.2 to Stable. It reduces unnecessary Jellyfin scans, fixes owned browser
process cleanup and adds optional Authenticator protection for individual accounts.

## Highlights

- **Coordinated Jellyfin scans.** Completed media is queued persistently and
  batched for 60 seconds. Royal respects running library tasks, waits at least
  five minutes between full scan attempts and bounds retries. Existing ffprobe
  validation rejects invalid or changing files; missing recognition never causes
  endless full scans. Movie badges, episodes and watchlist reconciliation remain.
- **Browser process cleanup.** Chromium/Xvfb and yt-dlp handles are waited after
  termination and forced kill. Partial startup, cancellation, resource failures
  and pool shutdown retain ownership until cleanup completes. The image runs
  under Tini so orphaned Chromium/Crashpad descendants have a suitable reaper.
  Download/probe concurrency is preserved; there are no global process-name kills.
- **Authenticator TOTP.** Accounts can enroll an Authenticator app, save one-use
  recovery codes and require their second factor on protected sign-ins/profile
  switches. Secrets are encrypted, codes have replay protection and account-wide
  attempt limits. Existing accounts are not automatically enrolled.
- **Clearer account and operating settings.** Operation/storage, account/security
  and automatic operation are reorganized. Installation details show the actual
  runtime; device migration requires an explicit target and valid paths rather
  than changing a cosmetic mode toggle. Personal profile/session management and
  household controls are clearer, including switching back to protected admins.
- **Own-domain access setup.** An administrator wizard prepares files for the
  operator's own domain and Cloudflare account, then verifies HTTPS and login
  protection. It preserves LAN access and current mounts; applying the tunnel
  configuration remains an explicit operator action.
- **Inbox and source monitoring.** Messages can be removed per account and remain
  hidden across polling/restart; new incidents can appear again. Technical source
  incidents are compact, backed by confirmed failed evidence and bounded repair
  attempts. Monitoring persistence and diagnostics avoid unnecessary foreground
  work and repeated writes.
- **Plex onboarding and security maintenance.** Alternative Plex media-center
  configuration is available alongside Jellyfin. Python/container/dependency
  security updates and mandatory Chromium/WebKit/performance gates are retained.

## Compatibility

Existing settings, users, subscriptions, queue state, media mounts and Stable
history are preserved. TOTP enrollment is optional. The central scan database
uses the existing persistent application data directory; do not remove it or
other state files as an update workaround. No deliberate breaking API change is
introduced. Health endpoints keep their existing payloads; capabilities and the
updater report application version `2.0.3` separately from the build revision.

Plex identities remain scoped to the configured token/server; configuration does
not silently impersonate arbitrary Plex Home users. Jellyfin remains supported.

## Known limitations

- A source-only application self-update inside an older container cannot install
  Tini or change the image entrypoint. **Update/rebuild the image and recreate the
  container normally to receive the complete zombie-prevention protection.**
- Targeted Jellyfin updates need paths as Jellyfin sees them. Separate Docker
  mount mappings cannot be inferred safely, so Royal uses strictly coordinated
  full scans. Unknown task status blocks an unchecked scan; the API token needs
  access to Jellyfin's scheduled tasks. External Jellyfin schedules/plugins/API
  clients remain outside Royal's coordinator.
- The exact origin of every zombie in the reported NAS snapshot is not proven.
  Offline process-tree tests establish cleanup/adoption behavior; normal overnight
  NAS observation is still needed after updating. No automatic media deletion or
  speculative ffprobe throttling was added.
- Older Android/TV clients need TOTP code-entry support before an enrolled account
  can log in. Own-domain publication requires the operator's domain/account and
  manual deployment of the prepared files; it is not automatic public hosting.

## Upgrade

Back up `.env`, complete `data/` and `runtime/`, media configuration and the current
source/image revision. Preserve mounts, credentials and authentication key files.
Review local source changes before switching revisions.

For a version-pinned source/image build:

```bash
git fetch --tags origin
git status --short
git switch --detach v2.0.3
docker compose config --quiet
APP_COMMIT_SHA="$(git rev-parse HEAD)" docker compose up -d --build
curl --fail http://127.0.0.1:8765/api/health
```

Verify version `2.0.3`, existing account access, protected profile switching,
queue/subscription recovery and both media mounts. Keep current volume/secret
mappings; do not use `down -v` or reset persistent data. Custom entrypoint
overrides must retain an init. Use the [NAS process verification guide](../NAS_PROCESS_VERIFICATION.md)
for targeted init, PID, zombie and resource checks after normal activity.
See [Jellyfin scan diagnostics](../JELLYFIN_SCANS.md) and
[release operations](../RELEASE.md) for the remaining operating checks.

## Rollback

Use the guarded versioned runtime rollback or a known-good source/image with
compatible backed-up state. Keep the data/runtime volumes and current backup;
never delete media or authentication keys to roll back. A source rollback does
not undo an image-level init change. Before exposing an older build externally,
verify that its login protection supports the enrolled authentication state;
older versions without TOTP cannot provide the new second-factor protection.
See [rollback operations](../RELEASE.md#rollback).

## Release verification

The release PR must pass the protected Quality gate before merging. The release
workflow repeats complete Quality on the Stable merge commit, then creates the
annotated `v2.0.3` tag and publishes the GitHub Release. Browser, Linux process-tree,
Tini image, security, performance and upgrade/rollback checks remain mandatory.
